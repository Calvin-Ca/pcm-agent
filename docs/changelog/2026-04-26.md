## B1 — 工时填报返回 HTTP 400

### 问题

用户输入「星期五，预管理系统，7.5 小时，完成回弹检测的后端开发」，收到：

```
❌ 服务错误: 服务调用失败: HTTP 400
```

### 根因

两处字段错误：

1. **`workhourDate` 格式**：SpringBoot DTO 期望 ISO Instant 格式 `2026-04-24T00:00:00.000Z`，旧代码直接传 `"2026-04-24"`（纯日期字符串），SpringBoot 反序列化失败。

2. **`description` 字段名**：上一 session 误将 `payload["description"]` 改为 `payload["workContent"]`（entity 字段名，非 DTO 字段名）。

3. **错误信息不透明**：`HTTPStatusError` catch 块没有提取 response body，用户无法看到 SpringBoot 的具体错误原因。

### 修复（`fastapi-service/app/tools/save_workhour.py`）

```python
# 修复前
payload = {
    "projectId": project_id,
    "workhourDate": date_str,      # ❌ 纯日期字符串
    "workhour": duration,
}
if description:
    payload["workContent"] = description  # ❌ 错误字段名

# 修复后
payload = {
    "projectId": project_id,
    "workhourDate": f"{date_str}T00:00:00.000Z",   # ✅ ISO Instant
    "workhour": duration,
}
if description:
    payload["description"] = description  # ✅ DTO 字段名
```

同时改进错误处理，提取 response body 并写入日志：

```python
except httpx.HTTPStatusError as e:
    try:
        err_body = e.response.json()
        err_msg = err_body.get("message") or err_body.get("msg") or str(err_body)
    except Exception:
        err_msg = e.response.text or ""
    logger.error(f"工时填报 API 调用失败: HTTP {e.response.status_code}, body: {err_msg}, payload: {payload}")
    return {"success": False, "error": f"服务调用失败: HTTP {e.response.status_code}" + (f" — {err_msg}" if err_msg else "")}
```

## B2 — 漏填工时查询结果为空（row_count=0）

### 问题

用户输入「查看我这个月有没有漏填工时」，SQL Agent 返回 `row_count: 0`，实际存在漏填。

### 根因

SQL 生成 Prompt（`sql_generation.yaml`）中漏填工时查询模板存在两处字段错误：

1. `wc.is_work_day='Y'` → 实际字段值为 `'1'`（VARCHAR 类型，`'0'`=非工作日，`'1'`=工作日）
2. 模板未包含 `wc.work_hour AS 应填工时`，用户无法看到每天应填多少小时
3. Prompt 缺少 `user_id` 和 `today` 变量，LLM 无法生成正确的 WHERE 条件

另外 `sql_query.py` 中 `_sanitize_row()` 未处理 Python `datetime.date` 对象，导致 JSON 序列化报错：`Object of type date is not JSON serializable`。

### 修复

**`fastapi-service/app/prompts/sql_generation.yaml`**

```yaml
# 新增 input_variables
input_variables:
  - table_schemas
  - permission_constraints
  - user_question
  - user_id    # 新增
  - today      # 新增

# 模板顶部新增
当前用户ID：{user_id}
今天日期：{today}

# 漏填工时模板修正
SELECT DATE(wc.date_value) AS 日期, wc.work_hour AS 应填工时
FROM work_calendar wc
LEFT JOIN workhour wh ON DATE(wc.date_value)=DATE(wh.workhour_date)
  AND wh.member_id='{user_id}'
WHERE wc.is_work_day='1'          -- 修正：'Y' → '1'
  AND DATE(wc.date_value) BETWEEN '{{start}}' AND '{{end}}'
  AND wh.id IS NULL
ORDER BY wc.date_value LIMIT 100
-- 说明：不要 JOIN sys_user 或 org_dept
```

**`fastapi-service/app/tools/sql_query.py`** — `_sanitize_row()` 新增日期处理：

```python
from datetime import date as _date_type, datetime as _datetime_type

def _sanitize_row(row):
    result = {}
    for k, v in row.items():
        if v is None:
            result[k] = None
        elif isinstance(v, _datetime_type):
            result[k] = v.strftime("%Y-%m-%d %H:%M:%S")
        elif isinstance(v, _date_type):
            result[k] = v.strftime("%Y-%m-%d")
        elif hasattr(v, '__float__') and not isinstance(v, (int, float, bool)):
            result[k] = str(v)   # Decimal
        else:
            result[k] = v
    return result
```

**`fastapi-service/app/tools/sql_query.py`** — `sql_query_handler` 传入新变量：

```python
from datetime import date as _date
sql_generation_prompt = pm.format(
    "sql_generation",
    table_schemas=table_schemas,
    permission_constraints=permission_constraints,
    user_question=question,
    user_id=user_id or "unknown",
    today=str(_date.today()),
)
```

## B3 — 加班时长查错表

### 根因

1. `compute_statistics.py` 工具描述中未排除「加班」场景，导致 LLM 路由到该工具

## B4 — SQL 查询响应展示原始 JSON

### 问题

sql_query 工具执行后，前端气泡框展示原始 JSON 对象，而非自然语言摘要。

### 根因

两层问题：

**后端**：`langgraph_agent.py` 在工具执行成功后，向前端推送 SSE `response` 事件时，只发了 `result`（原始工具输出对象），没有发 `message`（摘要文本）字段。

**前端**（`chat/index.ts`）：
- SSE `RESPONSE` 事件处理优先级：代码先判断 `e.result`，后判断 `e.message`，顺序反了
- `formatToolResult()` 对 sql_query 结果缺乏针对性处理，直接 fallback 到 `JSON.stringify`

### 修复

**`fastapi-service/app/services/langgraph_agent.py`** — 提取 summary 填入 message 字段：

```python
inner_result = result.get("result") if isinstance(result, dict) else None
summary_text = None
if isinstance(inner_result, dict):
    summary_text = inner_result.get("summary") or inner_result.get("message")
_collected_assistant_response = summary_text or _summarize_tool_result(log_tool_name, result)
yield _format_sse("response", {
    "result": result,
    "tool_name": log_tool_name,
    "message": summary_text,   # 前端优先展示此字段
})
```

**`web/src/store/modules/chat/index.ts`** — 调整 RESPONSE 事件优先级（message 优先于 result）：

```typescript
case SSEEventType.RESPONSE:
  if (e.chunk !== undefined) {
    // 流式文本块
    streamingContent += e.chunk
    ...
  } else if (e.message !== undefined && typeof e.message === 'string' && e.message.length > 0) {
    // ✅ 工具摘要或普通文本 — 优先展示
    streamingContent = e.message
    commit('UPDATE_MESSAGE', { ..., content: e.message })
  } else if (e.result !== undefined) {
    // fallback：结构化结果格式化
    const formatted = formatToolResult(e.result, e.tool_name)
    ...
  }
```

**`web/src/store/modules/chat/index.ts`** — `formatToolResult()` 新增 sql_query 处理：

```typescript
// sql_query 结果：优先展示 LLM 生成的摘要
if (inner.sql !== undefined || inner.question !== undefined) {
  const summary = inner.summary || ''
  const rowCount = inner.row_count ?? 0
  if (summary) return summary
  if (rowCount === 0) return '查询完成，未找到符合条件的数据。'
  return `查询完成，共 ${rowCount} 条数据。`
}
```

> **设计说明**：`summary` 字段由 `SQLAgentLLMClient` 在查询结束后调用一次独立 LLM（与主对话 LLM 共用同一 endpoint），将 SQL + 结果行转为自然语言摘要，再通过 SSE `message` 字段传给前端展示。

### E2E 验证路径

1. 输入任意 sql_query 场景（如「我这月有几天加班」）
2. 预期：气泡框展示自然语言摘要，不出现 `{` `}` JSON 符号
3. 如 LLM 摘要生成失败（row_count=0），展示「查询完成，未找到符合条件的数据。」

## B5 — `<think>` 块出现在摘要 / SQL 生成为空

### 问题

`sql_query.py` 内部独立调用 vLLM（qwen3-8b）时：
- 返回内容带 `<think>...</think>` 推理块，污染 SQL 字符串或摘要
- max_tokens=500 时，思考 token 耗尽配额，SQL 生成截断，工具报「SQL 为空」

### 根因

`SQLAgentLLMClient.generate()` 未禁用 vLLM 的 thinking 模式，也未对响应内容做 `<think>` 剥离。

原代码还判断 URL 中是否包含 `"ollama"` 来传参（`think: False`），但当前生产环境用的是 vLLM（`http://172.19.3.136:8099/v1`），参数名不同。

### 修复（`fastapi-service/app/tools/sql_query.py`）

```python
# 检测 URL 区分 Ollama / vLLM
_is_ollama = "ollama" in self._api_base.lower()
if _is_ollama:
    _thinking_param = {"think": False}
else:
    # vLLM 禁用思考模式：chat_template_kwargs
    _thinking_param = {"chat_template_kwargs": {"enable_thinking": False}}

payload = {
    "model": self._model,
    "messages": messages,
    "temperature": kwargs.get("temperature", 0.1),
    "max_tokens": kwargs.get("max_tokens", 800),
    **_thinking_param,
}

# 响应后剥离 <think> 块
content = _re.sub(r"<think>[\s\S]*?</think>", "", content, flags=_re.DOTALL).strip()
if "<think>" in content:                # 处理未闭合的 <think>
    content = _re.sub(r"<think>[\s\S]*", "", content, flags=_re.DOTALL).strip()
```

SQL 生成 max_tokens 从 500 提升至 2000（思考模式关闭后实际不消耗思考 token，保留余量应对长 SQL）：

```python
generated_sql = await llm_client.generate(
    messages=[...], temperature=0.1, max_tokens=2000,
)
```

### E2E 验证路径

1. 输入复杂查询（如「统计每个部门本月工时排名」）
2. 预期：响应摘要为自然语言，无 `<think>` 字符串
3. 查看 ai-service 日志，确认 `generated_sql` 是完整 SELECT 语句（无截断）

## B6 — 权限拒绝以 `response` 事件推送（前端展示成功）

### 问题

`employee` 角色查询他人工时，系统实际已拒绝，但前端收到的是 `response` 类型 SSE 事件，气泡框显示为正常消息而非红色错误提示。

### 根因

`task_executor.py` 中三个异常分支（`PermissionError`、`asyncio.TimeoutError`、通用 `Exception`）只返回了 `{"error": msg}`，没有加 `"success": False`。

`langgraph_agent.py` 收到结果后执行 `result.get("success", True)`，默认值 `True` 导致进入成功分支，推送 `response` 事件。

### 修复（`fastapi-service/app/services/task_executor.py`）

三个异常 return 全部补充 `"success": False`：

```python
except asyncio.TimeoutError:
    error_msg = f"任务执行超时 ({timeout}秒)"
    task.fail_execution(error_msg)
    return {"success": False, "error": error_msg}   # ✅ 补充

except PermissionError as e:
    error_msg = str(e)
    task.fail_execution(error_msg)
    return {"success": False, "error": error_msg}   # ✅ 补充

except Exception as e:
    error_msg = f"任务执行异常: {str(e)}"
    task.fail_execution(error_msg)
    return {"success": False, "error": error_msg}   # ✅ 补充
```

同时修复 `langgraph_agent.py` 中错误信息的嵌套提取（task_executor 将工具返回值包裹在 `result.result` 中）：

```python
inner = result.get("result") if isinstance(result, dict) else None
msg = (
    error
    or (result.get("error") if isinstance(result, dict) else None)
    or (inner.get("error") if isinstance(inner, dict) else None)
    or "工具执行失败"
)
```

1. 用 `employee` 角色账号登录

3. 预期：前端显示红色错误气泡「❌ 无权限查询他人工时」（而非正常消息格式）
4. 日志确认 `error` 类型 SSE 事件被发出

## B7 — FC 调用偶发文本格式 `<tool_call>` 而非 tool_calls 结构

### 问题

vLLM qwen3-8b 在输入 token 较多时，偶发将工具调用输出为文本格式：

```
<tool_call>{"name": "save_workhour", "arguments": {...}}</tool_call>
```

而非标准的 `finish_reason="tool_calls"` + `tool_calls` 结构，导致工具调用被跳过，走通用回复分支。

### 根因

vLLM qwen3-8b 模型在特定输入下行为不稳定，会降级为文本输出格式。

### 修复（`fastapi-service/app/services/llm_client.py`）

在 `generate_with_tools()` 中，当 `finish_reason="stop"` 且内容含 `<tool_call>` 时，fallback 解析文本：

```python
if "<tool_call>" in content:
    m = _re.search(r"<tool_call>\s*(\{.*?\})\s*(?:</tool_call>|$)", content, _re.DOTALL)
    if m:
        try:
            tc_data = _json.loads(m.group(1))
            name = tc_data.get("name") or tc_data.get("tool")
            args = tc_data.get("arguments") or tc_data.get("parameters") or {}
            if name:
                return {
                    "finish_reason": "tool_calls",
                    "content": None,
                    "tool_calls": [{"name": name, "arguments": args}],
                }
        except Exception:
            pass
```

同时将 FC 调用的 `max_tokens` 从 512 提升至 1024，为 tool_calls JSON 留出足够空间：

```python
result = await _llm_client.generate_with_tools(
    messages=messages, tools=tools, tool_choice="auto",
    temperature=0.1, max_tokens=1024, extra=extra,
)
```

### E2E 验证路径

1. 多次输入工时填报请求（变换不同描述长度）
2. 预期：每次都触发 `save_workhour` 工具调用，气泡显示「🔧 正在调用工具: save_workhour...」
3. 查看日志，确认无「LLM 选择通用回复」而应调用工具的情况

### B8 — M3 加班查询误路由到 RAG（P0）

**问题**
输入「查看我这周的加班时长」，LLM 路由到 `rag_engine`（knowledge_qa），而非 `sql_query`。

**上一轮错误归因（已修正）**
原以为是 `compute_statistics.py` / `sql_query.py` 的 tool description 不够强。但 RAG 路由发生在 **intent_classify 阶段**（FC 之前），跟 tool description 无关。真根因在意图分类的 prompt 示例偏差 + tools_desc 缺失。

**真根因（三级）**

1. **直接原因**：`node_classify_intent` → `route_intent` → `_classify_with_llm` 将"查看我这周的加班时长"判为 `knowledge_qa`（置信度 > 0.6），导致 `_route_by_intent` 走 `execute_rag` 分支。

2. **根因 A — intent_classify.yaml 示例偏差**：
   - 文件：`fastapi-service/app/prompts/intent_classify.yaml:14`
   - knowledge_qa 示例包含 `"加班怎么认定"`，将"加班"与知识问答强关联。
   - 用户输入"查看我这周的加班时长"不含"怎么/如何"等操作词，LLM 依据示例将其归为"想了解加班相关制度/知识"。

3. **根因 B — intent_router.py tools_desc 未包含 sql_query**：
   - 文件：`fastapi-service/app/services/intent_router.py:257-263`
   - `_classify_with_llm` 构造的 `tools_desc` 只列出 5 个工具（`query_timesheet` / `query_project` / `compute_statistics` / `generate_weekly_report` / `save_workhour`），**完全没有 `sql_query`**。
   - 即使 LLM 想判 `tool_execution`，也找不到能查 `workhour_attendance` 表的工具，只能 fallback 到 `knowledge_qa`。

4. **根因 C — query_timesheet 工具描述覆盖范围错误**：
   - 文件：`fastapi-service/app/services/intent_router.py:258`
   - `query_timesheet` 被描述为"查询工时填报明细记录"（指 `workhour` 表），加班数据在 `workhour_attendance` 表，LLM 不认为该工具适用。

**修复方向（本轮只记录，不改代码）**
- 方案 1（推荐）：在 `intent_classify.yaml` 的 `knowledge_qa` 示例中补充反向示例（"查看加班时长"不是知识问答），并在 `tool_execution` 示例中增加"查询本周加班时长"。
- 方案 2：在 `intent_router.py:257-263` 的 `tools_desc` 中追加 `sql_query` 工具说明。
- 方案 3：如果走的是 FC 主路径（`llm_with_tools`），检查 `_build_openai_tools` 中 `sql_query` 的 description 是否足够突出"加班"场景。

**E2E 验证**
172 直连，输入「查看我这周的加班时长」，响应 `route_info.target="rag_engine"`，预期应为 `tool_executor` + `sql_query`。

### B9 — M2 漏填查询 SQL 生成不一致（P0）

**问题**
- TC-01「本月漏填」生成 SQL 查 `workhour` 表（`SELECT DATE(wh.workhour_date) ... FROM workhour wh ... HAVING SUM(wh.workhour) = 0`），逻辑错误 —— 漏填应查 `work_calendar` 左连接 `workhour` 找出无记录的工作日。
- TC-02「本周漏填」SQL 正确（`work_calendar` + `is_work_day='1'` + `wh.id IS NULL`），但 **summary 与 row_count 矛盾**：row_count=5，summary 却说「没有未填写工时的日期」。
- TC-03「上周漏填」日期范围错误：生成 `BETWEEN '2026-04-19' AND '2026-04-26'`（本周），而非上周（4/13-4/19）。

**根因**
`sql_generation.yaml` 模板对「本月」和「本周/上周」生成不同的 SQL 路径，「本月」路径未使用正确的漏填模板；summary 生成 LLM 未正确读取 row_count；日期范围变量计算错误。

### 修复方案（草案，待审核）

**问题 1：「本月」路径未走漏填模板**
- 文件：`fastapi-service/app/prompts/sql_generation.yaml:25`
- 根因：模板中 `BETWEEN '{{start}}' AND '{{end}}'` 使用 f-string 转义后的占位符 `{start}` / `{end}`，LLM 需自行推断日期值。当用户问"本月"时，LLM 不确定 start/end 对应什么，自行构造了 `FROM workhour` + `HAVING SUM(wh.workhour)=0` 的错误逻辑。
- 修复草案：
  1. 移除模板中的占位符，改为在模板中直接写出日期计算方式示例：
     ```
     本月：BETWEEN DATE_FORMAT('{today}', '%Y-%m-01') AND '{today}'
     本周：BETWEEN DATE_SUB('{today}', INTERVAL WEEKDAY('{today}') DAY) AND '{today}'
     上周：BETWEEN DATE_SUB('{today}', INTERVAL WEEKDAY('{today}') + 7 DAY) AND DATE_SUB('{today}', INTERVAL WEEKDAY('{today}') + 1 DAY)
     ```
  2. 或在 `sql_query.py:328-335` 预计算 `start_date` / `end_date` 并注入 prompt 变量。

**问题 2：summary 与 row_count 矛盾**
- 文件：`fastapi-service/app/tools/sql_query.py`（SQLAgentLLMClient 摘要生成阶段）
- 根因：生成摘要的 prompt 未明确告知"row_count 表示结果行数，请据此判断是否有漏填"。
- 修复草案：在摘要生成 prompt 中强制要求：`"请先查看 row_count，如果 row_count > 0 则列出具体日期，如果 row_count = 0 则明确说明没有漏填。"`

**问题 3：「上周」日期范围错误**
- 文件：`fastapi-service/app/prompts/sql_generation.yaml:25`
- 根因：同上，LLM 对"上周"的日期范围计算错误。
- 修复草案：在模板中增加「上周」的明确示例，或在 sql_query.py 中通过正则提取时间词（本月/本周/上周），预计算 start_date/end_date 后替换到 user_question 中。

### B10 — save_workhour project_id 提取不稳定（P1）【已撤销】

**状态**：已撤销 —— 测试方法学问题，**非生产 bug**。

**原问题**
LLM 将 `[E2E TEST]` 前缀误认为项目名。例如输入「帮我填今天预管理系统 3 小时，[E2E TEST] 需求评审」，提取的 `project_id` 为 `[E2E TEST]`。

**撤销原因**
`[E2E TEST]` 是测试人员人为构造的输入标记，生产用户不会以方括号前缀输入此类文本。该问题不反映真实用户场景下的参数提取鲁棒性。后续测试改用 `(自动测试-请勿处理)` 作为后缀标记（见 §B12）。

### B11 — M3 部门加班排名 SQL 范围错误（P1）

**问题**
输入「统计本部门本周加班排名」，生成 SQL 中 `WHERE wa.member_id IN ('15999990206')`，仅查当前用户，未扩展到部门范围。

### 修复方案（草案，待审核）

**根因分析**
- 文件：`fastapi-service/app/prompts/sql_generation.yaml:29`
- 模板中加班查询固定使用 `WHERE wa.member_id='{user_id}'`，LLM 照抄此模板，未根据"部门"语义扩展范围。
- 当前 prompt 未注入 `department_id` 变量，LLM 无法知道当前用户所属部门。

**修复草案**
1. **prompt 变量扩展**：在 `sql_query.py:328-335` 将 `department_id` 注入 prompt（从 `context.get("department_id")` 获取）。
2. **新增部门统计模板**：在 `sql_generation.yaml` 中新增：
   ```yaml
   【部门加班统计模板】当问题含"部门"、"本部门"、"排名"时：
   SELECT su.entity_name AS 姓名, SUM(wa.overtime_hours) AS 加班总时长
   FROM workhour_attendance wa
   JOIN sys_user su ON wa.member_id = su.id
   JOIN org_dept od ON su.org_id = od.ext_field_2
   WHERE od.ext_field_2 = '{department_id}'
     AND wa.work_date BETWEEN '{{start}}' AND '{{end}}'
     AND wa.overtime_hours > 0
   GROUP BY su.id, su.entity_name
   ORDER BY SUM(wa.overtime_hours) DESC
   LIMIT 100
   ```
3. **规则强化**：在"生成规则"中增加第 8 条：
   `"当问题涉及'部门'范围时，必须使用 JOIN sys_user + org_dept 扩展查询范围，不得仅限制 member_id='{user_id}'。"`

### B12 — 测试输入标记规范

**背景**
B10 暴露出 `[E2E TEST]` 方括号前缀会被 LLM 误识别为项目名或参数值。需要统一测试输入标记规范。

**规范**
1. **标记位置**：作为描述文本的**后缀**，不要放在项目名/时长等结构化参数之前。
2. **标记格式**：`(自动测试-请勿处理)`
   - 使用圆括号包裹（降低被识别为结构化参数的概率）
   - 中文描述（LLM 对中文参数的提取更准确）
3. **示例**：
   - ✅ 正确：`帮我填今天预管理系统 3 小时，需求评审(自动测试-请勿处理)`
   - ❌ 错误：`帮我填今天预管理系统 3 小时，[E2E TEST] 需求评审`
   - ❌ 错误：`[自动测试]帮我填今天预管理系统 3 小时，需求评审`
4. **数据清理**：测试结束后执行 `DELETE FROM workhour WHERE description LIKE '%(自动测试-请勿处理)%'`

**适用范围**
所有 `docs/testing/modules/M*.md` 后续重跑、M5 压测、任何写入数据库的 e2e 测试。
