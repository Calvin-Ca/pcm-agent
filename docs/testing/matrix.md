## 优先级判定逻辑

### P0 — 简历定稿前必须全绿

**入选标准**：满足以下**任一**条件
- 上次浏览器实测出过血（B1~B7 全部命中 P0）
- 涉及"写操作"或"权限决策"，错了影响生产数据
- vLLM 模型层不稳定性（无法用接口测试覆盖）

**判定结果**：M1~M5

### P1 — 简历定稿后、离职前补完

**入选标准**：
- 用户高频但当前路径已工作的（M7 多轮、M8 默认兜底）
- 主路径并入 P0 验收的（M6 渲染并入 M2/M3）

**判定结果**：M6~M8

### P2 — 时间允许再做

**入选标准**：
- 改造成本高、收益主要在"健壮性"而非"正确性"
- 当前生产链路实际不会触发（M10 跨部门管理员极少）

**判定结果**：M9~M10

## 执行顺序建议

```
阶段 3 第 1 天（4/27 周日）
  └─ M1（填报）   ──┐
  └─ M4（权限）   ──┤  写操作 + 权限相关，先做
                   │
阶段 3 第 2 天（4/28 周一）
  └─ M2（漏填）   ──┤
  └─ M3（加班）   ──┤  SQL 模板族，一起做共用数据准备
                   │
阶段 3 第 3 天（4/29 周二）
  └─ M5（稳定性） ──┘  压测 50 次，单独占一天

阶段 5（5/1 后，可选）
  └─ M6/M7/M8（P1）
  └─ M9/M10（P2）
```

**为什么这个顺序**：
- M1/M4 先做：写操作出 bug 影响生产数据，权限漏洞最危险，先确认
- M2/M3 一起：都依赖 SQL 模板和真实库数据，准备一次共用
- M5 单独：50 次压测耗时 + 可能触发 vLLM OOM，要有富余时间排障

## 通过门槛

每个 P0 模块**必须三层全绿**才算通过：

| 层 | 要求 |
|---|------|
| 接口层 | SSE 流事件类型正确（`tool_call` / `response` / `error`），字段值符合预期 |
| 数据层 | 数据库 SELECT 比对：写操作有新记录 / 读操作字段名值正确 |
| 渲染层 | 浏览器气泡是自然语言、无原始 JSON、错误事件红色显示 |

任一层失败 → **挂在那个模块**，新建 bug 上报到 `docs/changelog/2026-04-XX.md`，**不跳过**。

## 与基准测试的关系

基准测试（`docs/benchmarks/`）和 e2e 测试（`docs/testing/`）**测试集不共享**：

- 基准测试用 `tests/benchmark/data/*.csv` 固定数据集，跑 50 次取分位数
- e2e 测试用真实生产库当前状态，跑 1 次确认行为

两者**目的互斥**：
- 基准测试要求**可重复**（同样输入 → 同样输出 → 同样指标）
- e2e 测试要求**真实**（用户当前真实数据 → 业务正确）

**冲突处理**：e2e 阶段（阶段 3）发现的 bug 修复后，**不重跑基准测试**。简历指标以 `docs/benchmarks/2026-04-25-final.md` 为准，冻结至 v1.3。
