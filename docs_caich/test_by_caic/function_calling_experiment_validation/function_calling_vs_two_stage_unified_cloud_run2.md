## 1. 测试配置

- 日期：2026-08-06
- 数据：项目当前完整单轮数据集，共2,000条
- 模型端点：DashScope OpenAI兼容API
- 模型：`qwen-plus`

- B组：一次Function Calling同时返回工具和参数
- 评测规则：每个方案、每条样本只调用一次完整架构，所有指标均从该次输出计算

A组31个错误均为：`AttributeError: 'list' object has no attribute 'strip'`，集中出现在多日期工时填报样本（`swhm_*`）。错误已按失败计入分母，不得从结果中剔除。该问题属于A组链路对列表型结果的兼容性问题，不是网络错误。具体原因是A组先执行意图分类，再由参数提取模型生成`save_workhour`参数；对于“今天和明天各填4小时”等多日期请求，参数提取结果中的`date`可能是日期列表，后续`node_classify_intent`将该值传给`_expand_multi_day_date()`，而当前函数按字符串处理`date_str`并直接调用`date_str.strip()`，因此收到列表时抛出异常并导致请求端到端失败。这31条是A组被测链路的真实运行时失败，不是统一评测脚本的参数评分异常。本Run仅记录原因，不修改业务实现；若后续修复列表型日期的校验与归一化，需要另起Run重新测试，不能回填或修正当前结果。

### 3.1 B组澄清准确率较低的原因

149条期望`clarify`的样本中，A、B均正确84条，A正确而B错误24条，A错误而B正确9条，两组均错误32条。因此A组正确数为`84 + 24 = 108`，B组为`84 + 9 = 93`，净差15条，即10.07个百分点。B组并非整体不具备澄清能力，**差距主要来自信息不足时仍选择工具，或把极短填报表达识别为闲聊。**

B组56条澄清失败样本中，46条输出`tool_execution`，10条输出`general_chat`。错误工具主要包括`query_timesheet`15条、`save_workhour`15条、`suggest_workhour`12条，另有`query_project`2条、`generate_weekly_report`1条和`compute_statistics`1条。

B组全部56条澄清失败可归纳为五类原因：第一，10条极短或语义不足的输入被识别为`general_chat`，说明“填报”“录入”“查询”“情况”等短表达缺少稳定的澄清兜底；第二，15条被误选为`query_timesheet`，主要是模型在查询与填报动作不明确时倾向直接查询，而不是询问用户目的；第三，15条在项目、日期或时长不完整时仍调用`save_workhour`，反映模型可能猜测参数，且写工具前缺少确定性的必填参数拦截；第四，12条调用`suggest_workhour`而非严格`clarify`，反映只读推荐与直接追问的产品策略和评测口径尚未统一；第五，4条误选`query_project`、`compute_statistics`或`generate_weekly_report`，说明这些工具的适用边界和负面约束仍不够清晰。另一方面，B组有9条A错误而B正确的样本，全部属于缺少时长场景，A组在这些样本上多次误选`query_timesheet`，说明B组并非整体不具备澄清能力，而是在上述五类边界场景中表现不稳定。

### 3.2 B组澄清准确率优化方案

优化应优先保证写操作安全，再处理意图和工具选择准确率：

| 对应问题 | 数量 | 优化措施 | 验收标准 |
|---|---:|---|---|
| 极短或语义不足输入误判为`general_chat` | 10 | 为“填报、录入、报工时、填工时”等写意图短表达增加低风险确定性规则，识别为参数不足并直接询问项目、日期和时长；“查询、情况、数据”等无法确定动作的短输入进入通用意图澄清，不得直接归入闲聊。 | 专项集`short_write_intent`的闲聊误判率为0；所有无法确定动作的短输入均返回澄清。 |
| 查询与填报不明确时误调用`query_timesheet` | 15 | 增加`query_or_write_ambiguous`动作消歧规则。对“今天在ERP升级项目”等只有项目、日期但没有查询或填报动作词的表达，询问“你是想查询该项目的工时，还是填报工时？”，不得强行选择查询或写入工具。 | 动作歧义样本直接选错工具率为0；消歧后工具选择准确率达到95%以上。 |
| 缺参时仍调用`save_workhour` | 15 | 在`TaskExecutor`或写工具入口对`is_write=True`的工具执行确定性校验。`save_workhour`缺少项目、日期或时长中的任意一项时禁止正式执行并强制`clarify`；参数只能来自当前消息、已确认会话状态或用户刚选择的候选项，不允许模型使用默认值或猜测值补齐。 | 缺参写操作误执行率为0；`missing_project`、`missing_duration`和`missing_two_or_more`专项集全部被安全拦截。 |
| 调用`suggest_workhour`而非严格澄清 | 12 | 统一产品策略：若允许辅助澄清，`suggest_workhour`必须保持只读，返回候选项目后继续收集日期和时长，最终写入前仍需预览确认；若不采用辅助澄清，缺少两个及以上必填参数时一律直接`clarify`。当前Run继续按严格口径记录，不对这12条事后改判。 | 分别报告严格澄清准确率和安全辅助澄清成功率；推荐工具写操作数为0；推荐后最终参数补齐率达到95%以上。 |
| 误调用`query_project`、`compute_statistics`或`generate_weekly_report` | 4 | 收紧工具正向描述和负面约束：`generate_weekly_report`仅处理明确的周报生成诉求；`compute_statistics`仅处理统计、汇总、占比和平均值；`query_project`不得用于工时填报补参；缺少明确动作时统一澄清。 | `wrong_tool_negative`专项集中上述三类工具误调用率为0。 |
| 所有写操作的提交安全 | — | 统一采用`dry_run → 用户确认 → 正式提交`。首次写调用由服务端强制`dry_run=true`并返回完整预览；将解析后的参数以`pending_write:{user_id}:{session_id}`保存到Redis，TTL为5～10分钟，并记录`operation_id`、参数Hash和`pending`状态。确认时校验用户、会话、有效期、权限、状态及参数Hash，再使用Redis原参数执行`dry_run=false`，不得重新让LLM生成参数或信任LLM自行输出的`confirm=true`。确认后更新为`completed`并用`operation_id`保证幂等；取消、过期和参数修改分别进入`cancelled`、`expired`或重新预览。`WRITE_DRY_RUN_DEFAULT=true`仅作为本地防误写安全阀。 | 未确认真实写入数为0；重复确认重复写入数为0；预览参数与正式提交参数一致率为100%；越权确认成功数为0。 |
| 回归数据与指标 | — | 建立`short_write_intent`、`missing_project`、`missing_duration`、`missing_two_or_more`、`query_or_write_ambiguous`、`safe_suggestion`和`wrong_tool_negative`专项回归集。 | 后续Run同时报告严格澄清准确率、安全辅助澄清成功率、最终参数补齐率、错误工具调用率和缺参写操作误执行率。 |

## 5. 结论与边界

本次完整、同模型、同数据、统一口径的Run 2支持以下结论：

1. B组Function Calling的联合端到端准确率比A组高25.35个百分点。
2. B组参数端到端准确率比A组高33.36个百分点，是主要收益来源。
3. B组平均延迟比A组低32.2%，整组墙钟时间低32.3%。
4. B组没有请求级错误；A组存在31个列表型结果兼容错误。
5. B组澄清准确率低于A组10.07个百分点，需要单独优化，不应只报告优势指标。

边界：本Run使用云端`qwen-plus`，不能替代生产vLLM `qwen3-8b`的验证；目前仍缺少同配置Run 3以及多轮复杂对话测试，尚不能宣称复杂对话稳定性已经得到完整证明。
