# RAG 混合检索、查询改写与重排序实验验证方案

> 验证对象：向量检索 + BM25 + 查询改写 + Reranker  
> 文档性质：检索消融实验与回答质量验收方案

## 1. 验证目标

验证以下组件对复杂问句和长尾场景的增量价值：

- 向量检索是否提升同义表达和自然语言改写问题的召回。
- BM25 是否提升专有名词、编号、制度名称和低频关键词命中。
- 混合召回是否形成互补。
- 查询改写是否改善多约束、多跳和口语化问题。
- Reranker 是否能将真正相关片段提升到上下文前列。
- 检索提升是否最终转化为答案完整性和事实正确率提升。

## 2. 统一实验规范

- 所有组使用相同知识库版本、文档切分、embedding 模型、生成模型和硬件。
- 固定最终上下文条数或 token 预算，避免某组通过输入更多文档获得不公平优势。
- 数据按问题模板划分为开发集 20%、验证集 20%、最终盲测集 60%。
- 每条生成用例至少重复 3 次，检索结果同时保留确定性单次统计。
- 保存查询改写、各路候选、融合分数、重排分数、最终上下文和回答。
- 使用配对 Bootstrap 报告指标差值及 95% 置信区间。

## 4. 数据集建设

项目现有 RAG 基准只有 50 条问题和 4 份文档，且问题直接从文档构造，纯向量 Recall@5 已达到 100%，存在明显天花板，不能充分证明 Hybrid 的收益。

建议将知识库扩充到至少 20 份文档，加入主题相似但答案不同的困难负样本，测试集不少于 200 条：

| 类型 | 特征 | 数量建议 |
|---|---|---:|
| 直接事实 | 可从单一段落直接定位 | 30 |
| 同义改写 | 不复用原文关键词 | 30 |
| 专有名词/编号 | 项目名、制度名、接口名、日期 | 30 |
| 长尾表达 | 口语、缩写、错别字和低频说法 | 30 |
| 多约束问题 | 同时包含角色、时间和业务条件 | 30 |
| 多跳问题 | 答案分布在两个以上章节或文档 | 30 |
| 无答案问题 | 知识库中不存在可靠答案 | 20 |

每条数据标注：标准问题、相关文档 ID、相关 chunk ID、必须回答的事实点、困难负样本、是否多跳、是否应拒答。

## 5. 评价指标

### 5.1 检索层

- Recall@5、Recall@10。
- Precision@5。
- MRR@10。
- nDCG@10。
- 多跳文档覆盖率。
- 困难负样本误排率。
- 无答案场景错误召回率。

### 5.2 回答层

- 答案事实正确率。
- 答案要点覆盖率。
- 引用文档和片段正确率。
- 无依据陈述率。
- 无答案正确拒答率。
- LLM 裁判得分与人工抽检一致率。

LLM 裁判只作为辅助指标。最终盲测至少人工复核全部失败案例和随机 20% 通过案例。

### 5.3 性能层

- 查询改写耗时。
- 向量与 BM25 检索耗时。
- Reranker 耗时。
- 完整链路 TTFT 和 E2E P50/P95。
- 输入 token 增量。

## 6. 验收标准

以纯向量检索为基线：

- 完整方案在长尾、专有名词集上的 Recall@5 提升至少 8 个百分点。
- 复杂和多跳问题的文档覆盖率提升至少 10 个百分点。
- MRR 或 nDCG 显著提升，证明相关片段不仅被召回，而且排序更靠前。
- 最终答案要点覆盖率提升至少 8 个百分点。
- 无依据陈述率不得上升。
- 无答案正确拒答率达到 95% 以上。
- P95 延迟增量必须拆分到改写、召回、重排和生成阶段。

## 7. 现有结果边界

当前小规模测试中，纯 Milvus Recall@5 为 100%，Hybrid Recall@5 为 98%。这是小知识库下 BM25 噪声占主导的合理结果，不能据此宣称 Hybrid 已提升召回。只有扩充文档、长尾表达和困难负样本后完成消融，才能验证设计价值。

## 8. 实施顺序

1. 冻结文档版本、切分策略、模型和上下文预算。
2. 扩充知识库并构造困难负样本。
3. 完成人工相关性标注和无答案标注。
4. 依次运行 A～F 六组检索实验。
5. 对相同检索结果运行回答生成与人工抽检。
6. 将失败问题固化为后续回归集。
