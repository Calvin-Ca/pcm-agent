## 各版本说明

### v1：建立基线

首次使用 Ollama qwen3:8b 对完整 2000 条用例进行测试，得到 53.6% 的通过率。报告重点分析了两类问题：意图判断错误，以及已判断为工具请求但选择了错误工具。

### v2：抽样定位问题

选取典型用例和历史失败用例，快速验证 Prompt 修改与规则兜底是否有效。该版本不是完整 Benchmark，不能将抽样通过率与其他版本的 2000 条整体通过率直接比较。

验证发现，类似“工时数据”这样的短句仅靠 Prompt 调整仍容易被判为普通对话，需要考虑规则兜底或更强的模型能力。原报告中的 RAG TTFT 内容已拆分至独立 RAG 报告。

### v3：验证第一轮优化

重新执行完整 2000 条测试，通过率由 53.6% 提升至 56.7%。结果表明第一轮优化有一定效果，但多天填报、按项目查询等已知薄弱场景仍未解决。

### v4：切换 vLLM

将推理服务从 Ollama 切换至 vLLM qwen3-8b，并继续验证 Prompt 修复。整体通过率提升至 62.9%，说明推理框架、模型服务配置以及相关 Prompt 调整对 Function Calling 表现产生了明显影响。

### v5：修复工具 Schema 与业务逻辑

主要修改包括：放宽 `save_workhour` 必填字段、调整 `description` 定义、增加多天日期展开、在澄清结果中保留工具名，以及修正测试数据。整体通过率提升至 68.9%，多天填报类提升最明显，但缺少项目时的澄清用例仍暴露出返回字段不一致问题。

### v6：优化模型生成配置

调整 vLLM 参数并增大 `max_tokens`，降低模型输出被截断或无法解析的概率，同时更新部分测试期望。整体通过率提升至 79.9%，多天填报达到 100%，但边缘用例和按项目统计仍是主要失败来源。

### v7：集中处理意图消歧

针对知识问答、按项目统计、月统计等容易混淆的场景补充规则、工具描述和消歧示例。整体通过率达到 87.0%，完成预设的 85% 目标；剩余问题主要集中在复杂边缘表达和少量闲聊误判。

## 演进路线

```text
v1 建立完整基线
 → v2 抽样定位失败原因
 → v3 验证第一轮优化
 → v4 切换推理框架
 → v5 修复工具 Schema 和业务逻辑
 → v6 优化模型生成配置
 → v7 完善细分类别消歧
```

## 结果解读

从 v1 的 53.6% 到 v7 的 87.0%，提升并非完全来自模型能力，还同时包含以下因素：

- Prompt 和工具描述优化；
- Ollama 切换至 vLLM；
- Function Calling Schema 调整；
- 多天填报及澄清等业务代码修复；
- `max_tokens` 等推理参数调整；
- 部分测试数据和期望结果修正。

因此，这组报告反映的是整个意图识别与 Function Calling 系统的迭代效果，不能直接作为单纯的模型能力对比。
