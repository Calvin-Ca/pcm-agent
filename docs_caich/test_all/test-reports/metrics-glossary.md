# 性能与精度测试指标说明

本文档说明 `benchmark_llm.py` 与精度测试中涉及的所有指标含义，供读取测试报告时参考。

---

## 一、性能指标

### 1.1 延迟类指标

#### TTFT（Time To First Token，首 Token 延迟）

**定义**：从发出请求到收到流式输出第一个 token 的时间。

**为什么重要**：对用户感知影响最大。用户点击发送后，页面"动起来"的等待时长。TTFT 越低，交互感越好。

**影响因素**：
- LLM Prefill 阶段耗时（处理输入 prompt 的时间）
- 网络往返时延（RTT）
- RAG 场景还包括：向量检索 + Reranker 的耗时（在调用 LLM 之前完成）

**参考值（本项目）**：
- chat/tool 场景：1.5-2.5s 可接受
- RAG 场景：当前 10.71s，目标 <3s
- 超过 5s 用户会明显感到卡顿

---

#### TPOT（Time Per Output Token，每 Token 生成耗时）

**定义**：从第一个 token 输出后，平均每生成一个 token 所需的时间，单位 ms。

**计算方式**：`(总耗时 - TTFT) / 输出 token 数`

**为什么重要**：决定流式输出的"打字速度"。TPOT 越低，文字流出越流畅。

**参考值**：
- qwen3:8b：~7.5ms/token（约 133 token/s）
- qwen3:4b：~5.2ms/token（约 192 token/s）
- 人眼感知阈值：超过 50ms/token（20 token/s）会感觉卡顿

---

#### ITL（Inter-Token Latency，Token 间隔延迟）

**定义**：相邻两个 token 之间的实际间隔时间。理论上等于 TPOT，但实际受批处理、网络抖动影响会有波动。

**与 TPOT 的区别**：TPOT 是平均值，ITL 是逐 token 的瞬时值，更能反映流式输出是否均匀。

---

#### Jitter（抖动，ITL 标准差）

**定义**：ITL 的标准差，衡量 token 间隔的稳定性。

**为什么重要**：Jitter 高意味着输出忽快忽慢，用户会感知到"卡一下再刷一段"的不流畅感，即使平均速度相同。

**参考值**：本次测试 Jitter 均为 0-2ms，属于稳定范围。

---

### 1.2 吞吐量类指标

#### TPS（Tokens Per Second，每秒生成 token 数）

**定义**：整个响应过程中，服务端平均每秒生成的 token 数量。

**计算方式**：`输出 token 数 / 总耗时`

**注意**：TPS 受输出长度影响。输出越长，TTFT 占比越小，TPS 越接近真实 decode 速度。短输出的 TPS 偏低，不代表模型慢。

**参考值**：
- qwen3:8b：40-70 TPS（工具调用/分析场景）
- qwen3:4b：100-130 TPS（decode 更快，但 TTFT 更高）

---

#### RPS（Requests Per Second，每秒请求数）

**定义**：并发测试中，服务在单位时间内处理的完整请求数量。

**与 TPS 的区别**：TPS 是单请求维度（token 速度），RPS 是系统维度（吞吐能力）。

**参考值**：本次测试 8 并发下 RPS=3.58，对于工时系统的实际并发量（通常 <10）完全够用。

---

### 1.3 分布类指标

#### P50 / P95 / P99（百分位延迟）

**定义**：
- **P50**：50% 的请求延迟低于此值（中位数，代表典型体验）
- **P95**：95% 的请求延迟低于此值（代表大多数用户的体验上限）
- **P99**：99% 的请求延迟低于此值（代表极端情况，如慢请求）

**为什么用 P95/P99 而不是均值**：均值容易被少数极慢请求拉高，掩盖真实情况。P95 更能反映用户实际感受到的"慢"。

**参考值**：本次 8 并发 TTFT p95=2.24s，表示 95% 的请求首 token 在 2.24s 内返回。

---

## 二、精度指标

### 2.1 核心指标

#### 失败率（Failure Rate）

**定义**：测试用例中，模型输出与期望标签不匹配的比例。

**计算方式**：`失败数 / 总用例数`

**本次结果**：qwen3:8b 失败率 46.4%，qwen-plus 历史参考约 20%。

---

#### Intent 准确率

**定义**：模型正确识别用户意图（tool_execution / general_chat / clarify / knowledge_qa / complex_request）的比例。

**本次主要问题**：565 条 tool_execution 被误判为 general_chat，即模型在用户实际想查工时/填报时，错误地认为用户只是在闲聊。

---

#### Tool_name 准确率

**定义**：在意图正确识别为 tool_execution 的前提下，工具选择是否正确的比例。

**本次主要问题**：75 条 query_timesheet 被误判为 compute_statistics，两者语义边界模糊（"工时统计"既像查询也像计算）。

---

### 2.2 失败类型分类

| 类型 | 说明 | 修复方向 |
|------|------|---------|
| intent 错误 | 意图被判错（如 tool_execution → general_chat） | Prompt 引导 |
| tool_name 错误 | 意图正确但工具选错 | 工具描述细化 |
| 参数错误 | 工具正确但参数填错 | 参数提取 Prompt |

---

## 三、指标之间的关系图

```
用户体验
  ├─ "等多久才看到第一个字" → TTFT（越低越好）
  ├─ "文字流出快不快" → TPOT / Jitter（越低越好）
  └─ "说的对不对" → Intent 准确率 / Tool_name 准确率（越高越好）

系统能力
  ├─ "能同时服务多少人" → RPS / 并发稳定性
  └─ "长文本生成效率" → TPS
```
